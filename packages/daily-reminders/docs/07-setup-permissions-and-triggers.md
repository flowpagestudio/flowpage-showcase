# Daily Reminders — אתחול, הגדרות, טריגרים והרשאות

## 1. מטרת המסמך

להגדיר כיצד מקימים את סביבת הנתונים וההרשאות של המערכת באופן בטוח וחוזר.

המסמך מכסה:

- אתחול Google Sheets.
- בדיקת מבנה.
- הגדרות מערכת.
- טריגרים.
- הרשאות.
- בדיקות פתיחה.
- טיפול באתחול חוזר.
- התאוששות מתקלות.

## 2. סביבת המערכת

המערכת תורכב מ:

- פרויקט Google Apps Script.
- Google Sheet לשמירת הנתונים.
- Google Calendar להתראות.
- Web App כממשק משתמש.
- GitHub כמקור קוד ותיעוד.

בגרסה הראשונה המערכת מיועדת לחשבון Google יחיד.

## 3. תהליך הקמה ראשוני

### שלב 1 — יצירת Google Sheet

יש ליצור קובץ Google Sheet ייעודי לפרויקט.

שם מומלץ:

Daily Reminders — Data

אין לשלב את הנתונים בגיליון של פרויקט אחר.

### שלב 2 — יצירת Apps Script

יש ליצור פרויקט Apps Script ייעודי.

שם מומלץ:

Daily Reminders — Apps Script

הפרויקט צריך להיות מקושר לחשבון Google המיועד לשימוש במערכת.

### שלב 3 — קישור ל־Sheet

יש לשמור את מזהה הגיליון בהגדרת מערכת או ב־Script Properties.

אין להכניס את המזהה ישירות לקוד ציבורי אם ניתן להימנע מכך.

### שלב 4 — הפעלת Setup

פונקציית האתחול:

- תבדוק את קיום הגיליון.
- תיצור את הגיליונות החסרים.
- תיצור כותרות.
- תכניס הגדרות.
- תבדוק תקינות.
- תיצור טריגרים.
- תכתוב Log.

## 4. שם הגיליונות

ה־Setup ייצור את הגיליונות הבאים:

- Reminders
- ReminderInstances
- Settings
- Logs

אם גיליון קיים:

- אין למחוק אותו.
- אין ליצור עותק נוסף.
- יש לבדוק את הכותרות.
- יש להחזיר שגיאה אם חסרה עמודה קריטית.

## 5. בדיקת מבנה

המערכת תבדוק:

- שכל הגיליונות קיימים.
- ששורת הכותרות קיימת.
- שכל שדה חובה קיים.
- שאין כותרות כפולות.
- שאין שינוי לא מוכר בשמות העמודות.
- שהגדרות החובה קיימות.

### תוצאה אפשרית

#### תקין

המערכת ממשיכה ומסמנת INITIALIZED=true.

#### חסר

המערכת לא תכתוב נתוני עסק, ותציג אילו רכיבים חסרים.

#### מבנה פגום

המערכת תעצור ותכתוב שגיאה ל־Logs.

## 6. הגדרות ברירת מחדל

ה־Setup ייצור את ההגדרות הבאות:

| key | value | תיאור |
|---|---|---|
| APP_NAME | Daily Reminders | שם המערכת |
| TIMEZONE | Asia/Jerusalem | אזור הזמן |
| DEFAULT_GENERATION_WINDOW | 30 | מספר ימים קדימה |
| UPCOMING_VIEW_DAYS | 7 | תצוגת ימים קרובים |
| MINIMUM_LEAD_MINUTES | 1 | מרווח מינימלי לעתיד |
| DEFAULT_NOTIFICATION_MINUTES | 0 | התראה בזמן האירוע |
| CALENDAR_NAME | Daily Reminders | שם יומן יעד |
| APP_VERSION | 1.0.0 | גרסת המערכת |
| SCHEMA_VERSION | 1 | גרסת המבנה |
| INITIALIZED | false | מצב האתחול |

## 7. יומן Google Calendar

### אפשרות מומלצת

יצירת יומן ייעודי בשם:

Daily Reminders

יתרונות:

- הפרדה מאירועים אישיים.
- צבע נפרד.
- קל יותר לבדוק סנכרון.
- ניתן למחוק או לנקות רק את אירועי המערכת.

### כלל

ה־calendarId יישמר ב־Settings לאחר יצירת היומן.

אם היומן כבר קיים:

- יש להשתמש בו.
- אין ליצור יומן כפול.
- יש לשמור את המזהה.

## 8. הרשאות נדרשות

המערכת תדרוש הרשאות ל:

- קריאת Google Sheets.
- כתיבה ל־Google Sheets.
- יצירה ועדכון אירועים ב־Google Calendar.
- הרצת Apps Script.
- שימוש ב־Lock Service.
- שימוש ב־Properties Service.

בשלב הראשון אין צורך בהרשאות:

- Gmail.
- Drive כללי.
- Contacts.
- WhatsApp.
- SMS.

## 9. שלבי אישור הרשאות

1. הפעלת פונקציית בדיקת הרשאות.
2. קבלת בקשת ההרשאה של Google.
3. אישור החשבון הנכון.
4. אישור Sheets.
5. אישור Calendar.
6. הרצת בדיקת יצירה.
7. בדיקת הופעת אירוע ביומן.

אין לפרסם את ה־Web App לפני שההרשאות נבדקו.

## 10. סוג פריסת Web App

בגרסת MVP:

- Execute as: המשתמש שמריץ את האפליקציה.
- Who has access: המשתמש בלבד או משתמשים מורשים, לפי הגדרת החשבון.
- אין לפתוח גישה ציבורית ללא צורך.
- כתובת ה־Web App נשמרת במסמך הפריסה.

## 11. טריגרים

### 11.1 Trigger תחזוקת מופעים

מטרתו:

- לבדוק התראות פעילות.
- לזהות טווח מופעים קצר מדי.
- ליצור מופעים חסרים.
- לסנכרן מופעים עם שגיאה.

תדירות מומלצת בגרסת MVP:

- פעם ביום.

### 11.2 Trigger תחזוקת סנכרון

מטרתו:

- לבדוק SYNC_ERROR.
- לנסות סנכרון חוזר.
- לאתר אירוע חסר.
- לעדכן מצב סנכרון.

תדירות אפשרית:

- פעם בשעה או פעם ביום.

בשלב הראשון ניתן לשלב אותה ב־Trigger התחזוקה הראשי.

### 11.3 Trigger ניקוי וארכוב

לא חובה בגרסה הראשונה.

בעתיד:

- ארכוב Logs ישנים.
- ארכוב מופעים ישנים.
- שמירה על ביצועי הגיליונות.

## 12. מניעת טריגרים כפולים

בעת יצירת טריגרים:

1. חיפוש טריגר קיים לפי שם פונקציה.
2. אם קיים — לא ליצור חדש.
3. אם חסר — ליצור.
4. לתעד את הפעולה ב־Logs.

Setup חייב להיות אידמפוטנטי: ניתן להריץ אותו מספר פעמים ללא יצירת כפילויות.

## 14. אתחול חוזר

אם INITIALIZED=true:

- אין ליצור מחדש גיליונות.
- אין למחוק נתונים.
- אין לאפס Settings.
- יש לבדוק SCHEMA_VERSION.
- יש לבצע תיקון מבני רק אם הוגדר מנגנון migration.

## 15. שינוי גרסת סכימה

כאשר המבנה משתנה:

1. קריאת SCHEMA_VERSION.
2. השוואה לגרסת הקוד.
3. הפעלת migration מתאים.
4. גיבוי או תיעוד השינוי.
5. עדכון הגרסה.
6. כתיבת Log.

בגרסה הראשונה אין לבצע שינוי עמודות אוטומטי שעלול למחוק נתונים.

## 16. התאוששות מתקלות

### גיליון נמחק

- המערכת תזהה את החסר.
- לא תיצור גיליון חדש אוטומטית אם קיימים נתונים לא ברורים.
- תציג הוראות התאוששות.
- תאפשר Setup מחדש לאחר אישור.

### יומן נמחק

- המערכת תציג שהיומן חסר.
- ניתן ליצור יומן חדש.
- יש לשמור calendarId חדש.
- אירועים ישנים לא ישוחזרו אוטומטית.

### טריגר נמחק

- בדיקת בריאות תזהה את החסר.
- Setup יוכל ליצור אותו מחדש.
- תירשם פעולה ב־Logs.

### הרשאה בוטלה

- פעולת נתונים תיכשל באופן ברור.
- תוצג הודעת הרשאה.
- אין למחוק רשומות מקומיות בגלל כשל הרשאה.
